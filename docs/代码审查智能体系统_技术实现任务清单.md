> **上游文档**: [PRD (v2.0)](./PRD_代码审查智能体系统.md) | [架构设计](./代码审查智能体系统_架构设计与功能方案.md) | [Skill](./code-review-agent.skill)

> **总工期估算**: 10 周（1 人全职），6 周（2 人并行）

---

## 核心修正说明

**OpenEvolve 的定位**：进化**被审查的代码本身**（发现更好的算法、更低的复杂度、更高的性能），而不是进化审查 Agent 的 Prompt。

```
审查 Agent 发现"可自动优化"问题 → OpenEvolve 进化代码 → 输出优化版本作为修复建议
```

Prompt 仍由人工维护和调优，不走 OpenEvolve。

## Phase 0: Spike 验证

**工期**: 2 天 | **优先级**: 🔴 最大的未知数先验证  
**目标**: 验证 OpenEvolve 能否在保持功能不变的情况下降低代码复杂度

### 任务清单

| # | 任务 | 技术要点 | 验收标准 | 估时 |
|---|------|---------|---------|------|
| 0.1 | 准备测试样本 | 选 3-5 个真实的高复杂度函数（圈复杂度 15-30）+ 其功能测试用例 | 每个样本有可运行的 pytest 测试 | 2h |
| 0.2 | 安装并配置 OpenEvolve | `pip install openevolve`，配置 Gemini Flash API，初始化评估器 | `openevolve` CLI 可正常运行 | 2h |
| 0.3 | 编写代码进化评估器 | `evaluate_code(program_file) → EvaluationResult`：功能测试（硬门控）+ 圈复杂度 + 行数 + 性能 benchmark | 评估器返回正确的 metrics + artifacts | 4h |
| 0.4 | 跑 3-5 个样本进化 | population_size=60, num_islands=4, max_iterations=200，观察复杂度下降幅度 | 至少 1 个样本复杂度降低 > 30% 且功能测试通过 | 4h |
| 0.5 | 人工审查进化结果 | 将 OpenEvolve 产出的代码 + diff 给同事 review | 采纳率 > 40%（同事愿意用进化版本） | 2h |

**Phase 0 产出**: 确认 OpenEvolve 能有效降低代码复杂度，值得继续投入。如果 Spike 不通过（采纳率 < 30%），需要重新评估方向。

**依赖**: 无。这是整个项目的网关——不通过则后续全停。

## Phase 1: 静态门控

**工期**: 1 周 | **优先级**: 🔴 止血 - 先阻断最差代码  
**目标**: PR 提交后 2 分钟内返回复杂度/安全/Lint 检查结果

### 模块: Static Gate (`src/gate/`)

| # | 任务 | 技术要点 | 验收标准 | 估时 |
|---|------|---------|---------|------|
| 1.1 | 初始化项目骨架 | `pyproject.toml` + `src/` 目录结构 + `cra` CLI 入口 | `pip install -e .` 成功 | 3h |
| 1.2 | 复杂度检查器 | `radon` 解析 AST，对每个函数判断是否 > 15 | 输入文件 → `[(func, cyclomatic, line, verdict)]` | 4h |
| 1.3 | 安全硬阻断规则 | 正则 + AST：SQL 拼接、硬编码密钥、裸 except | 输入文件 → `[(line, rule_id, evidence)]` | 6h |
| 1.4 | Lint/Format/类型检查集成 | 封装 `ruff check --fix` / `mypy`，解析输出 | 返回结构化 JSON | 3h |
| 1.5 | 门控汇总器 | 汇总 1.2-1.4 结果，WARN/SOFT_BLOCK/HARD_BLOCK 三级 | 🔴 阻断项存在时 exit code != 0 | 3h |
| 1.6 | CI 模板 + pre-commit | GitHub Actions YAML + `.pre-commit-config.yaml` | PR 自动触发；本地 `git commit` 自动检查 | 2h |

**Phase 1 产出**: 每个 PR 自动检查，复杂度/安全问题直接阻断。

**依赖**: Phase 0 通过。

## Phase 2: 审查 + 代码进化引擎

**工期**: 2.5 周 | **优先级**: 🔴 核心价值 - 从"告诉你问题"到"帮你修好"  
**目标**: 审查 Agent 识别可优化问题 → OpenEvolve 进化代码 → 输出进化版本作为修复建议

### 模块 2A: 审查 Agent (`src/agents/`)

| # | 任务 | 技术要点 | 验收标准 | 估时 |
|---|------|---------|---------|------|
| 2.1 | LLM Client 抽象层 | `litellm` 统一接口，支持 OpenAI/Gemini/Ollama，含重试 + 超时 + fallback | 三个 backend 可切换，失败自动 fallback | 6h |
| 2.2 | Agent Prompt 管理 | 从 `references/agent-prompts.md` 加载 System Prompt，支持模板变量 | Prompt 文件化，和代码分离 | 3h |
| 2.3 | Security Agent | 调用 LLM + Security Prompt，解析返回 JSON | 对预置 SQL 注入代码返回 🔴 | 4h |
| 2.4 | Complexity Agent | 同上 | 对预置高复杂度代码返回指标 + 分类标记 | 3h |
| 2.5 | Performance Agent | 同上 | 对预置 N+1 查询代码返回具体问题 | 3h |
| 2.6 | Readability Agent | 同上 | 对预置魔法数字代码标记问题 | 3h |
| 2.7 | Style Agent | 不调 LLM，复用 Phase 1 lint 结果 | 返回 🟡/💭 标记 | 2h |
| 2.8 | 问题分类器 | 将 Agent 发现的问题分为两类：🧠 需人工判断（安全怎么修、架构）vs 🤖 可自动优化（复杂度高、性能差、可读性差）| 分类准确率 > 80%（人工验证） | 4h |

### 模块 2B: 代码进化引擎 (`src/evolver/`)

| # | 任务 | 技术要点 | 验收标准 | 估时 |
|---|------|---------|---------|------|
| 2.9 | OpenEvolve 配置模块 | 封装 OpenEvolve 配置：population_size=60, num_islands=4, exploitation_ratio=0.7, 特征维度=[complexity, performance, readability] | 配置可通过 YAML 修改 | 3h |
| 2.10 | 代码进化评估器 | `evaluate_code(program_file, test_file) → EvaluationResult`：功能测试（硬门控，不通过直接淘汰）+ 圈复杂度（radon）+ 性能 benchmark（timeit）+ 可读性（LLM 1-10 分）+ 产物侧信道（stderr, profiling） | 返回符合 OpenEvolve 格式的 EvaluationResult | 6h |
| 2.11 | 进化任务调度器 | 接收问题分类器的"可自动优化"问题列表 → 对每个问题调用 OpenEvolve 进化（可并行）→ 收集结果。限制每次审查最多触发 3 个进化任务（控制成本） | OpenEvolve 完成 → 返回进化后代码 + 前后对比 | 6h |
| 2.12 | 进化结果验证 | 进化后代码必须通过原始功能测试 + Phase 1 静态门控（复杂度/安全/Lint）| 不通过 → 输出失败原因 | 3h |

### 模块 2C: Arbiter + 报告 (`src/arbiter/`)

| # | 任务 | 技术要点 | 验收标准 | 估时 |
|---|------|---------|---------|------|
| 2.13 | 去重 + 冲突解决 | 按 file:line 合并重叠问题，优先级：Security > Correctness > Complexity > Performance > Readability > Style | 两个 Agent 报同一位置 → 合并 | 4h |
| 2.14 | 报告生成器 | 标准 Markdown 报告：🔴 阻断项（含 OpenEvolve 进化后代码 + diff）、🟡 建议项、📊 进化前后对比（复杂度、性能变化）、代码健康度评分 | 格式符合 PRD 定义 | 4h |

### 模块 2D: 反馈收集

| # | 任务 | 技术要点 | 验收标准 | 估时 |
|---|------|---------|---------|------|
| 2.15 | PR Comment 解析 | 识别 `@review:accept` / `@review:reject` / `@review:evolve:accept`（采纳进化版本）指令 | 审查员回复 → 系统捕获并记录 | 4h |
| 2.16 | 反馈存储 | SQLite: `reviews` + `review_issues` + `evolution_results` 表 | 可查询进化代码的采纳率、复杂度变化趋势 | 3h |

**Phase 2 产出**: 审查 Agent 发现问题 → 可自动优化的交给 OpenEvolve 进化 → 审查报告含进化前后对比 → 开发者一键采纳。

**依赖**: Phase 1 + Phase 0 通过。

## Phase 3: Prompt 优化与反馈闭环

**工期**: 3 周 | **优先级**: 🟡 从"能用"到"越用越好"  
**目标**: 基于反馈数据持续调优 Agent Prompt + 知识库建设

### 模块 3A: Prompt 调优 (`src/prompts/`)

| # | 任务 | 技术要点 | 验收标准 | 估时 |
|---|------|---------|---------|------|
| 3.1 | Prompt 版本管理 | Git-based Prompt 版本控制，每次修改记录原因 + 预期效果 | 可追溯每次 Prompt 变更 | 3h |
| 3.2 | Prompt A/B 测试框架 | 同一 PR 分流：50% 用当前 Prompt，50% 用候选 Prompt；对比采纳率 | A/B 结果可统计检验（p < 0.05） | 6h |
| 3.3 | Prompt 性能监控 | 按 Agent 统计 precision（采纳率）、recall（检出率）、fpr（误报率）| 可视化面板显示各 Agent 质量趋势 | 4h |

### 模块 3B: 知识库 (`src/knowledge/`)

| # | 任务 | 技术要点 | 验收标准 | 估时 |
|---|------|---------|---------|------|
| 3.4 | 反模式库 | YAML 存储：`{pattern_id, description, examples, severity, occurrence_count}`，从反馈数据中自动提取被多次驳回的相同模式 | 检出已知反模式时自动匹配 + 计数 | 6h |
| 3.5 | 最佳实践库 | YAML 存储：`{practice_id, description, code_example, context}` | 审查报告中引用相关最佳实践 | 4h |
| 3.6 | OpenEvolve 进化历史 | 存储每次进化的输入/输出/diff/采纳结果/复杂度变化 | 可按采纳率分析哪种类型代码进化效果最好 | 4h |

### 模块 3C: 评估器权重调优 (`src/evolver/weighting.py`)

| # | 任务 | 技术要点 | 验收标准 | 估时 |
|---|------|---------|---------|------|
| 3.7 | 反馈驱动的权重调整 | 基于"进化代码是否被采纳"的反馈数据，调整 `evaluate_code` 中各维度（复杂度/性能/可读性）的权重 | 进化代码采纳率随反馈积累而上升 | 4h |

**Phase 3 产出**: Prompt 持续调优体系 + 反模式/最佳实践知识库 + 进化引擎评估权重自适应。

**依赖**: Phase 2 的反馈数据（至少 2 周积累）。

## Phase 4: 度量看板与 CI 集成

**工期**: 2 周 | **优先级**: 🟡 从"工具"到"平台"  
**目标**: Tech Lead 可视化掌握代码质量趋势

### 任务清单

| # | 任务 | 技术要点 | 验收标准 | 估时 |
|---|------|---------|---------|------|
| 4.1 | 代码健康度趋势 API | FastAPI: `GET /api/trends?repo=X&period=30d` | JSON 响应，支持按仓库/时间段筛选 | 4h |
| 4.2 | 进化效果 API | `GET /api/evolution/stats`：进化总次数、采纳率、平均复杂度降幅、MAP-Elites 网格填充率 | 数据可追溯至每次进化任务 | 3h |
| 4.3 | Streamlit 看板 | 单页仪表盘：健康度趋势 + Agent 准确率 + 进化采纳率 + 成本趋势 | Tech Lead 打开即看 | 6h |
| 4.4 | 成本 + 延迟监控 | 记录每次 LLM API token 消耗和耗时，按 Agent/进化任务聚合 | 成本异常（日增 > 50%）告警；P95 < 10 min | 4h |
| 4.5 | 私有化部署支持 | Ollama 集成测试 + 文档，确保敏感代码仓库可用本地模型（审查 + 进化都支持）| 切换 `model: ollama/llama3` 后功能正常 | 4h |

**Phase 4 产出**: 度量看板 + 成本/延迟监控 + 私有化部署。

**依赖**: Phase 3（反馈数据）。
